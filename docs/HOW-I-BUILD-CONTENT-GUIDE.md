# How I Build Content Guide — Standards & Editorial Rules

## 1. Core Editorial Philosophy
Every claim, methodology step, and decision pattern must be **derived from actual project history**.

### Prohibited Patterns:
- ❌ **Generic SDLC Diagrams:** Do not copy generic corporate textbooks (`Agile Scrum 2-week sprints`, `Waterfall requirements sign-off`) unless explicitly documented.
- ❌ **Skill Percentages:** Never use "Python 95%", "React 90%", or skill progress bars.
- ❌ **Inflated Self-Ratings:** Do not write "Expert", "World-class", "Industry-leading", or "Rockstar".
- ❌ **Fabricated Metrics:** Do not write "Boosted ROI by 340%" or "Saved 10,000 engineering hours" without empirical backing.

### Mandatory Patterns:
- ✅ **Evidence-First Citing:** Every principle and step must link to verifiable project slugs (`deep-learning-stock-return-prediction`, `curasphere-hms`, `multi-agent-prospect-intelligence`, `market-regime-engine`).
- ✅ **Concrete Technical Questions:** Focus on real questions asked during system design (e.g. data leakage, lookahead bias, state machine boundaries, touch target ergonomics).
- ✅ **Transparent Trade-offs:** Explicitly state what was sacrificed (e.g. boilerplate overhead, EM algorithm parameter sensitivity, token latency).
- ✅ **Distinguish Aspirations from Practice:** Mark future research as roadmap/limitations, keeping established practices grounded in public repositories.
